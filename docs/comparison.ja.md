## 既存ツール

### Claude Code Sandbox

[Claude Code Sandbox](https://code.claude.com/docs/en/sandboxing) はOSレベルのプリミティブ（macOSのSeatbelt、LinuxのBubblewrap）を使って、ファイルシステムへの書き込みとネットワークアクセスを制限します。パーミッション設定で `Read` のdenyルールを追加し、特定ファイルへのAIの読み取りをブロックすることもできます。

**強み：**
- OSレベルの実行制限（macOSは追加セットアップ不要。Linux/WSL2では `bubblewrap` と `socat` のインストールが必要）
- Readのdenyルールで特定ファイルへのアクセスをブロック
- パーミッション確認の手間を軽減

**本プロジェクトが埋めるギャップ：**
- denyルールはアプリケーションレベル — 正しい設定とAIツールがそれを尊重することに依存
- denyルールは[親ディレクトリを走査しない](https://github.com/anthropics/claude-code/issues/12962)ため、モノレポやマルチプロジェクトワークスペースで、あるプロジェクトの設定が兄弟プロジェクトのシークレットを保護しない
- Dockerコマンドはdockerソケットへの直接アクセスを必要とするため、サンドボックスの仕組みと構造的に相容れない。[公式ドキュメントのトラブルシューティング項目](https://code.claude.com/docs/en/sandboxing#troubleshooting)自体が`docker *`を`excludedCommands`（サンドボックス対象外）に指定することを推奨しており、結果としてDockerを使った操作はサンドボックスの保護を一切受けずに、無制限のホスト権限で実行される

### Docker AI Sandboxes

[Docker AI Sandboxes](https://docs.docker.com/ai/sandboxes) はAIエージェントを独自のDockerデーモンを持つ隔離されたmicroVMで実行します。エージェントはホストシステムに触れることができません。

**強み：**
- microVMによる強力な分離
- Sandbox内でのAIエージェントの完全な自律性
- 各Sandboxが独自のDockerデーモンを持つ

**本プロジェクトが埋めるギャップ：**
- ワークスペースディレクトリ全体をmicroVMに同期し、特定ファイルを除外する仕組みがない — `.env`ファイルは内部で見える。これは実装の不備ではなく設計目的の違いによるもの：Docker AI Sandboxesは「AIエージェントの実行からホストを守る」ことが目的であり、「AIからシークレットを隠す」ことはそもそも設計スコープに含まれていない
- 完全に隔離されており、各Sandboxは他のコンテナと通信できないため、コンテナ間デバッグが不可能

### Docker MCP Toolkit

[Docker MCP Toolkit](https://www.docker.com/blog/mcp-toolkit-mcp-servers-that-just-work/) は200以上のコンテナ化されたMCPサーバーを、組み込みの分離とシークレット管理付きで提供します。

**強み：**
- 豊富なビルド済みMCPサーバーカタログ
- MCPサーバー設定のための組み込みシークレット管理

**本プロジェクトが埋めるギャップ：**
- MCPサーバーの分離に焦点を当てており、プロジェクトレベルのシークレットをAIから隠すことは対象外
- ソースツリー内の`.env`ファイルや秘密鍵の問題には対応していない

## 本プロジェクトが追加するもの

AI Sandbox + HostMCPは、上記のツールが完全にはカバーしない2つのギャップを埋めます：

### ギャップ1: ファイルシステムレベルのシークレット隠蔽

ルールでシークレットへのアクセスをブロックする（設定ミスやバイパスの可能性がある）代わりに、Dockerボリュームマウントを使ってシークレットをAIのファイルシステムから**物理的に除去**します：

```yaml
volumes:
  - /dev/null:/workspace/my-app/.env:ro     # AIには空ファイルに見える
tmpfs:
  - /workspace/my-app/secrets:ro            # AIには空ディレクトリに見える
```

シークレットはAIの世界に存在しません — ルールでブロックされているのでも、設定でフィルターされているのでもなく、そもそも存在しない。一方、アプリコンテナは実ファイルを通常通りマウントします。

設定ミスに対しては、Sandbox起動時に**バリデーション**を実行し、AIツールのdenyルールと`docker-compose.yml`のボリュームマウントが同期しているかを確認します。片方にしか設定されていないシークレットファイルがあれば、AIがアクセスする前に警告が表示されます。さらに別のチェックで、どちらの設定にも一切宣言されていないシークレットらしきファイルをAIのセッション開始のたびに検出します。そのため開発作業時に作られたファイルの設定漏れの可能性を早期に発見することができ、対象のファイルが対処が必要な秘匿ファイルなのか、そのまま放置しても問題ないファイルなのかAIが対処方法を尋ねてきます。

### ギャップ2: 制御されたコンテナ間アクセス

HostMCPはAI SandboxとDockerコンテナの間のゲートウェイとして機能し、セキュリティポリシーを適用します：

- AIはログの読み取り、ホワイトリストに登録されたコマンドの実行、コンテナの検査が可能
- AIはブロックされたパスへのアクセスや任意のコマンドの実行はできない。コンテナの起動/停止はデフォルトで無効化されており、設定で明示的に有効化した場合のみ可能
- 機密データ（パスワード、APIキー、トークン）は出力時に自動的にマスクされる
- HostMCP自体はデフォルトでループバックアドレス（127.0.0.1）にのみバインドされるため、初期状態ではネットワーク上の他のマシンからアクセスできない

## 組み合わせて使う

これらのツールは、性質の異なる2種類のレイヤーに分けて考えると位置づけが明確になります。

### 隔離境界：脅威モデルに応じて「選択」するもの

Docker AI SandboxesとAI Sandbox（本プロジェクト）は、どちらも「AIエージェントの実行環境全体をどこで区切るか」を担う選択肢です。前者はmicroVM、後者はコンテナ＋ボリュームマウントによるシークレット除去という異なるアプローチを取りますが、役割が重複するため、両方を重ねて使う想定にはなっていません。脅威モデルに応じてどちらか一方を選びます。

Claude Code Sandboxは対象が異なり、Bashコマンドの実行のみをOSレベルで制限する仕組みなので、選んだ外側の環境の内側に追加でネストできます。ただしAI Sandboxのような非特権コンテナ内にネストする場合、[公式ドキュメント](https://code.claude.com/docs/en/sandboxing#troubleshooting)にある通りbubblewrapがフレッシュな`/proc`をマウントできず`enableWeakerNestedSandbox`が必要になることがあり、その場合ネストしたサンドボックスのプロセス空間隔離は外側のコンテナ境界に依存する形になります（パーミッションのdenyルール自体はこの影響を受けず機能し続けます）。そのため「AI Sandbox内部でネストすれば最大限の保護が得られる」とは言い切れず、上乗せ効果はあるものの限定的です。

| 隔離境界の選択肢 | 役割 |
|-----------------|------|
| Claude Code Sandbox | Bashコマンドの実行をOSレベルで制限（他の境界にネスト可、ただし上記の留意点あり） |
| Docker AI Sandboxes | microVMでAIエージェント全体を隔離 |
| **AI Sandbox**（本プロジェクト） | コンテナ隔離＋ボリュームマウントでシークレットをAIのファイルシステムから除去 |

### パーミッション層：独立して併用可能

HostMCP（本プロジェクト）のコンテナ間アクセス制御や、Managed Settingsのdenyルールは、隔離境界とは階層が異なります。ツール呼び出し単位でのアクセス可否を制御するものなので、上記のどの隔離境界を選んでも独立して重ねて使えます。

## まとめ

| 機能 | Claude Code Sandbox | Docker AI Sandboxes | 本プロジェクト |
|------|-------------------|-------------------|--------------|
| 実行制限 | OSレベル | microVM分離 | コンテナ分離 |
| ファイル読み取りブロック | denyルール（アプリケーションレベル） | 仕組みなし | ボリュームマウント（ファイルシステムレベル） |
| マルチプロジェクトスコープ | 制限あり（親ディレクトリ走査なし） | 単一ワークスペース | ワークスペース全体＋ファイル単位の隠蔽 |
| コンテナ間アクセス | 制限あり | 隔離 | HostMCPで制御 |
| 出力のシークレットマスク | なし | なし | 自動 |
| 起動時バリデーション | なし | なし | 自動同期チェック |
| セットアップの複雑さ | macOSは不要／Linux・WSL2はbubblewrapとsocatが必要 | Docker Desktop | Docker + docker-compose |
